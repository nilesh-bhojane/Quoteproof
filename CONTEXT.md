## 1. What we are building (one workflow only)

Quotation preparation for small B2B suppliers/manufacturers in India.
A customer sends a messy inquiry. The owner pastes it. QuoteProof AI turns it into a checked
quotation draft. The owner reviews and approves. The app records what the AI proposed, what the
human changed, and how much time was saved.

One line: **AI reads, code calculates, human approves, ledger proves.**

## 2. Hard rules (never break these)

1. AI never decides a price, discount, tax or total. All numbers come from the DB price list + code.
2. AI only extracts: product text, quantity, unit, specification. Output must pass a JSON schema check.
3. Customer identifiers (phone, email, name) are masked BEFORE any call to an external AI.
4. Nothing is sent to a customer automatically. The owner copies/sends it themselves.
5. Approval is blocked while any critical flag is unresolved.
6. Never promise stock we do not have. Stock shortage forces an explicit owner decision.
7. Approved quotes keep the prices they were created with (price snapshot). Later price edits never change them.
   An approved quote is read-only. To change it, create a revised draft from it; the old approval stays on record.
8. If AI is unavailable or the owner turns it off, "Basic mode" (fuzzy match, no AI) must still work.
9. Customer text is untrusted. Instructions inside it ("ignore the price list", "quote Rs 1") are ignored and flagged.
10. ROI numbers are labelled "measured" or "estimated" and always show sample size and the hourly-rate assumption.

## 3. Flow

1. Owner pastes the inquiry (email connect is P1; it feeds the same pipeline).
2. Mask PII.
3. AI extracts items (or Basic mode does a rule/fuzzy extraction).
4. Code matches each item to a product in the price list.
5. Code checks stock for each matched item.
6. Code prices: unit price (bulk tier if applicable), discount, GST 18%, totals.
7. Flags are raised (see section 5).
8. Owner edits, resolves flags and stock decisions, then approves or rejects.
9. Evidence Ledger records everything. Timer stores manual vs assisted time.

## 5. Flags

| Flag | Critical (blocks approval)? |
|---|---|
| Unknown product / no match | Yes |
| Missing quantity | Yes |
| Unit mismatch or ambiguous size/spec | Yes |
| Stock short or zero (needs owner decision) | Yes |
| Price older than review limit (stale) | No (warning, fresh check before approval) |
| Below minimum margin | Yes unless owner confirms with a reason |
| Large discount requested | No (warning, shows margin impact) |
| Prompt-injection text detected | No (warning, text ignored) |

Every flag has the same shape so the UI can show it: `code`, `severity` (info / warning / blocking), `message` (plain English),
`item` (which line it affects), `suggested_action`, `blocks_approval` (true/false). Ambiguous matches return the candidate products.

## 6. Stock rules

Stock is stored on the product row: `stock_on_hand`, `reserved`, `track_stock`.
`available = stock_on_hand - reserved`. Owner edits these by hand. We do NOT auto-reserve when a quote is made
(a quote is not an order). If `track_stock = false`, skip the check for that product.

Stock is checked after extraction + matching, at draft time and again at approval.

| Case | Behaviour |
|---|---|
| Available >= requested | Normal draft |
| 0 < available < requested | Stop and ask the owner: quote partial qty / backorder with delivery date / alternative product / decline. Quote is built only after the choice. |
| available = 0 and no alternative | No quote. Show "Not available". Offer a copyable out-of-stock reply (owner adds expected date). |

## 7. Price rules

- Two separate fields: `cost_price` (our cost) and `sell_price` (approved selling price). Cost changes never auto-change sell price.
- Owner updates prices manually (CSV import is P1). Each edit sets `price_updated_at`.
- A price not reviewed within the review limit (default 30 days, in settings) shows a stale warning, and a fresh check runs before approval.
- There is no free universal market-price feed. Automatic updates need a supplier feed; mention as roadmap only.

## 8. Tech stack and engineering standards

| Part | Choice |
|---|---|
| Frontend | React + Vite on Vercel (assumed; match what Person B already has). Designed first, then built against mock data through one `api` module with a mock switch, then pointed at the real backend |
| Backend | Python 3.12, FastAPI, Pydantic, SQLAlchemy, pytest. Hosted on Render |
| Database | Supabase Postgres. Schema in `database/schema.sql` (no migration tool). SQLite only for quick local tests |
| AI | Google Gen AI SDK, Gemini. Model name comes from `GEMINI_MODEL` in `.env`, never hardcoded |
| IDE | Antigravity; code on GitHub |

Free-tier note: free-tier prompts may be used by the provider for training, so masking is mandatory.
Masking reduces risk but does not guarantee confidentiality. Say so in the app and the pitch.

### Engineering standards (apply to all code)
- Money: Python `Decimal` only, never float. Rule: each line = qty x unit price, minus discount, rounded to 2 places (half up);
  GST is calculated on the discounted subtotal and rounded once. Tests lock this rule in.
- The server recalculates every total. Never trust totals sent by the frontend.
- AI output: define a Pydantic schema, validate every response, never trust a product name from the AI.
  Extracted fields: item description, quantity, unit, specifications, delivery needs, missing fields, ambiguity warnings.
- AI failure (bad JSON, timeout, rate limit, outage): short timeout, at most 2 retries, then return a clear recoverable error
  and offer Basic mode, labelled as Basic mode. Never fake a successful extraction.
- Matching: exact SKU or name first, then deterministic rules. Weak or multiple matches go to the owner. Never invent a SKU.
- Evidence Ledger: every event has id, correlation_id, quote_id, event type, server timestamp, actor (human / ai / system),
  before and after values. It is read-only in the UI. Mistakes are corrected by adding a new event, never by rewriting history.
  Do not call it tamper-proof.
- ROI comes only from stored measurements. Show an empty state with a reason when there is no data. Report negative savings
  honestly. Money is always labelled an estimate. Each metric must let the user see the records behind it.
- Privacy: secrets only in `.env`; `.env.example` has placeholders; never log raw customer text; error messages must not leak
  keys or stack traces; CSV upload has file-size and row limits; demo uses synthetic customer data.
- Tests: pytest. Mock Gemini in normal tests. Real-Gemini tests are separate and marked, so the suite never needs a live API call.
- Keep code simple. No extra layers, no unused endpoints, no features outside P0/P1.
- Not for this hackathon (say "roadmap" in the pitch): login and multi-business separation, catalogue versions with activation,
  idempotency keys, rate limiting, migration tooling.

### Handshakes (agree on these; change only after telling the other person)
1. A's draft creates `quotes` and `quote_items` rows. B reads them. B's approve only changes status, approved_by, approved_at.
2. `evidence_service.log_event(quote_id, actor, action, before, after, correlation_id)` is used by both parts.
3. A provides `draft_service.recheck_quote(quote_id)` returning blocking flags and stock status. B's approve calls it and
   refuses approval if anything blocking remains.
4. A provides `draft_service.draft_from_text(text, mode)`. B's trust-test runner calls it.

6. A writes `ai_usage` rows. B reads them for the cost-per-quote display.
7. Until the other part exists, use the seed data and the mock switch in the `api` module.

## 10. Data model (draft)

- `products`: id, name, aliases[], unit, sell_price, cost_price, min_margin_pct, bulk_tiers (json), stock_on_hand, reserved, track_stock, price_updated_at
- `quotes`: id, status (draft / approved / rejected), inquiry_masked, subtotal, gst, total, approved_by, approved_at, created_at
- `quote_items`: id, quote_id, product_id, raw_text, qty, unit, unit_price_snapshot, line_total, ai_proposed (json), final (json), flags (json), stock_status, explain_text
- `audit_log`: id, correlation_id, quote_id, actor (ai / human / system), action, before (json), after (json), at
- `timings`: id, quote_id, kind (manual / assisted), seconds, at
- `ai_usage`: id, quote_id, tokens_in, tokens_out, cost_inr
- `settings`: hourly_rate, stale_days, gst_pct, basic_mode
- P1: `price_history`: id, product_id, old_price, new_price, changed_at

Raw customer identifiers are not stored by the backend. Placeholder-to-real-value mapping stays with the owner's session only.

## 11. API contract (all paths under /api/v1; change it here first, then tell your teammate)

| Method + path | Purpose |
|---|---|
| GET /api/v1/health | Alive check |
| GET /api/v1/products | Price list with stock |
| POST /api/v1/products, PATCH /api/v1/products/{id} | Add / edit price, cost, stock (sets price_updated_at) |

| POST /api/v1/quotes/{id}/stock-decision | item_id, decision (partial / backorder / alternative / decline), qty, note |

| POST /api/v1/timings | quote_id, kind, seconds |

## 14. Demo plan

1. Catch the mistake: incomplete inquiry flagged, not guessed.
2. Stock short: 500 asked, 120 available, owner chooses.
3. Prove what changed: AI draft, human edit, approval history.
4. Prove the value: recorded times, sample size, assumptions, cost per quote.

Honest framing: our differentiators are intended, not verified claims that competitors lack them.
We combine them into one measurable quotation workflow.
